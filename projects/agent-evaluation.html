Workstream 1

Adversarial evaluation tasks

A task is only useful if a strong model can fail it for a real reason. Mine have to meet three conditions at the same time. The naive reading of the data looks correct and is wrong. The cases that decide the answer are hidden from the sample the agent sees, yet fully determined by it. And the result can still be graded byte-exact, so passing or failing is never a judgement call.

Each task ships self-contained. This is the path one task takes from idea to accepted submission.

  1. Design the trap

    Choose a problem where the obvious interpretation of the data is plausible and wrong, and where the deciding cases never appear in the sample but follow from it.

  2. Generate the data

    Build a synthetic corpus for the task instead of borrowing real data, which keeps every case that matters under control.

  3. Prove there is exactly one answer

    Show computationally that the corpus admits exactly one consistent interpretation. Where a task hides structure, I recover it with integer linear algebra and modular arithmetic.

  4. Write the reference solution

    Solve the task by genuine computation, the way an agent would have to, with nothing hard-coded.

  5. Pin the environment

    A digest-pinned Dockerfile builds the environment for both the agent and the verifier, so both work against the same pinned environment.

  6. Grade the real output

    A pytest suite checks what the agent actually produced, byte-exact, instead of matching strings in its answer.

  7. Pass the review gates

    The task goes in as a pull request and iterates against automated review gates until every check is green. Across three programmes, every one of my submissions has been accepted.

Workstream 2

Repositories rebuilt at a historical commit

Some tasks start from real open-source code. The job is to take an arbitrary repository at a specific commit from its history and make it build and test again, reproducibly.

  1. Check out the commit

    Start from the exact historical commit the task is based on.

  2. Write a build recipe

    Capture how that repository builds in its own recipe, so the environment comes out the same every time it is rebuilt.

  3. Pin until the suite flips

    Pin dependencies until the test suite that failed before the fix passes after it.

  4. Verify against the reference

    Confirm that fail-to-pass flip against the reference solution before the environment ships.

Workstream 3

Submission pipeline tooling

Tasks move through a submission pipeline that spans several folders, and a pipeline like that will happily build the same thing twice. I wrote the tooling that stops it.

Per-repository build recipes

Every repository gets its own recipe, so its environment can be rebuilt the same way on any day.

Collision detection

New work is checked against a shared ledger, so two submissions do not end up covering the same ground.

Build locks

Only one build of the same thing can run at a time.

Dedupe caches

Work that has already been built is recognised and reused instead of being built again.
